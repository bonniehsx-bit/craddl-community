# 充值商品化 — 实施记录

> 状态:**已完成**(2026-08-21)。原「开发计划」里的 SKU 方案已被推翻,本文是最终落地形态。

---

## 一、为什么要改

初版把充值做成「插件私有档位表 + 代码偷建的隐形占位商品」:

```php
RechargeGoodsHelper::ensureGoods()   // new Goods(); $g->save(false);
```

三个硬伤:

1. **运营看不见** —— 后台商品列表 `GoodsListForm` 只列 `type=normal`,占位商品是隐形的,
   **永远配不了分销** → 「将来客户想让充值也分润」做不到。
2. **绕过 `GOODS_AFTER_SAVE`** —— `save(false)` 不走商品表单,所有分润插件的
   `GoodsListener` 从没见过它,自然没有配置行。
3. **核心 SKU 定价能力没用上**,多一层「档位 ↔ 订单金额」的自维护关系。

---

## 二、被推翻的中间方案:用核心 SKU 当档位

试过,**做不下去**,两个硬伤:

1. `SkuGenerator.vue` 的表格列是写死的(价格/成本价/采购价/库存/重量/编码/预览图),
   所有商品共用、没有插槽。为充值加一列「赠送额」会污染所有商品的规格表。
2. **更致命**:`generateSkus()` 新生成的规格行**连 `id` 字段都没有**
   (老规格按 specs 组合 key 复用)。新建商品时规格只是前端内存里的组合,
   **没有 `attr_id`** —— 插件面板无从挂靠赠送额。

改用 voucher 的 `plugin_voucher_bundle_item` 范式:档位是**插件自己的子表**。

## 三、最终结构

```
Goods「余额充值」  type='withdraw_recharge'      ← 运营在插件商品管理页可见可编辑
   ├─ plugin_withdraw_recharge_goods   goods_id → 到账钱包(一个商品一个钱包)
   └─ plugin_withdraw_recharge_plan    goods_id → 档位(实付/到账/赠送/限购/身份/排序)
   
   plugin_withdraw_recharge_order      充值单(快照 + 到账幂等锁)
```

### 🔴 必须记住的不变量

**`RechargeGoodsListener::GOODS_TYPE` 必须等于 `WithdrawRechargeOrderHandler::getOrderType()`**
(都是 `withdraw_recharge`)。

下单管线里 handler 分两处解析、依据不同:
- `mainHandler`(preview / fillOrderData) → 按 `form->type`
- 逐商品(`checkStockAndPermission` / `saveOrderDetail`) → 按 **`$goods->type`**

不一致时明细阶段会落到 `NormalOrderHandler`,`createForOrder` 根本不执行 →
充值单不存在 → **付款成功但永远不到账**,而订单看起来一切正常。
(plaza 在线购电就栽在这上面,见 `plugins/plaza/CLAUDE.md §9.21`。)
`withdraw-classcheck/order-routing` 有断言锁死。

## 四、核心代码零改动

靠三个核心早就留好的扩展点:

| 扩展点 | 用途 |
|---|---|
| `GoodsForm` 接受任意 `type`(`GoodsBaseSavePipe:41` 原样写入) | 插件商品不用在核心注册,**不加 `Goods::TYPE_*` 常量** |
| `GoodsEditDrawer` 的 `disable-multi-spec` / `hidden-tabs` / `#extra-tabs` 插槽 | 商品编辑页可裁剪、可扩展,**不碰 SkuGenerator / app-base-goods-panel** |
| `GOODS_EDIT_FORM_LOAD` / `GOODS_AFTER_SAVE` | 插件配置自己挂载 |

因此**不需要** `BasePlatformGoodsEditForm` / SavePipe / 插件 GoodsController ——
后端只有一个 `RechargeGoodsListener`。

> 注入 pluginData 时**故意不带 `component_name`** —— 带了是走 `app-base-goods-panel`
> 的动态组件(给"要出现在所有商品编辑页"的插件用,如分销);充值只属于自己,走插槽。

## 五、已定的业务决策

| # | 决策 | 落点 |
|---|---|---|
| 1 | 充值**不参与优惠券 / 积分抵扣** | preview 管线不挂 `ApplyDiscountStage` + 自带 `FormatRechargePreviewStage`;C 端走插件专属下单页。`selectedCoupon` 恒 null,券也不会被核销 |
| 2 | 赠送与本金**进同一钱包** | 一次 `AssetService::credit(本金+赠送)` |
| 3 | 一个商品一个钱包 | 要充余额和积分就建两个商品(还能各自配不同分销比例) |

> ⚠️ **决策 2 的已知敞口**:赠送额进了可提现钱包,存在「充 100 送 10 → 提现 110」的套利。
> 这是**有意接受**的取舍(换设计简单)。要堵可在提现侧用手续费 / 门槛兜。

## 六、要不要给充值分润

**由分润插件按商品自行决定,充值这边不做任何排除。**

运营编辑充值商品时,「分销设置」tab 会自然出现(`distribution\GoodsListener::editLoad`
对任何商品都注入面板)—— 不勾就不参与,勾了才参与。

> 遗留议题(与充值无关):`DistributionListener` 的 `if ($distGoods && !$distGoods->is_commission_open)`
> 在**商品无配置行**时会跳过守卫、按全局比例照发。UI 标签、DB 默认值、其余四家分润插件
> (dealer/area/xwy/brand)都是「没配 = 不参与」的口径,唯独这行相反。
> 改动会让 `distribution-test` 的 66 条断言里 16 条挂掉(那套测试是照着现行行为写的),
> **需要业务侧拍板**,已还原未改。充值商品化之后**不受它影响**(有配置行,开关说了算)。
